# smartdns — локальный умный резолвер

Локальный DNS-сервер, который решает одну задачу:

> У меня есть «умный» резолвер (например `111.88.96.50` / `https://xbox-dns.ru/dns-query`),  
> который подменяет адреса AI-сервисов на рабочие. Но он же гадит — отдаёт `0.0.0.1`  
> там, где не должен. Значит: спрашиваем его первым, смотрим ответ, и если он  
> погадил — молча идём к следующему DNS по цепочке.

Всё DNS-поведение настраивается **одним файлом `smartdns.yaml`**. Параметров  
командной строки почти не осталось. Единственное, что живёт вне конфига —  
через какой транспорт пакеты доходят до апстримов: это маршруты ОС (см.  
«Архитектура» ниже).

---

## Архитектура: что где живет

smartdns — DNS-прокси (форвардер): принимает запросы на себя (UDP/TCP 53,  
DoT 853), кэширует, отбраковывает мусор и пересылает апстримам по цепочке.  
**В коде нет ничего «жесткого»**: что слушать, у кого спрашивать, в каком  
порядке и что считать мусором — всё в `smartdns.yaml` (пустой конфиг —  
`127.0.0.1:53` и дефолтные cloudflare/google, любой пункт перекрывается).

Прокси до апстримов — единственное, чего в smartdns **нет вовсе**: ни строчки  
SOCKS/HTTP в коде, ни опции в конфиге. Транспорт решает ОС — на vdska так:

```
клиент ──UDP/TCP 53──┐
клиент ──DoT 853─────┤
                     v
                  smartdns ──1.1.1.1────────── ip rule, table 100 → WARP (США)
                           ──tls://[2606:4700::…] IPv6-маршрут → USA-прокси, мимо WARP
                           ──4.2.2.x─────────── напрямую (аварийный уровень)
```

Эти маршруты прописаны на сервере скриптом `warp-usa-up.sh`, переживают  
ребут и меняются **отдельно** от smartdns.yaml — DNS-конфиг трогать не надо  
(и наоборот: перестройка цепочки апстримов не лезет в маршруты). Подробно  
эта часть разобрана в `warp-usa-on-vdska.md`, а готовый конфиг установки  
(юниты, маршруты, серты, проверочные команды) — в отдельном пакете  
`vdska-deploy.zip`, не в этом.

Итого, кто за что отвечает:

| Слой                    | Файл/механизм                  | Что решает                                                              |
| ----------------------- | ------------------------------ | ----------------------------------------------------------------------- |
| DNS-поведение           | `smartdns.yaml`                | слушатели, апстримы, цепочки, отбраковка, кэш, прогрев, DoT-сертификаты |
| Транспорт до апстримов  | маршруты ОС (`warp-usa-up.sh`) | через WARP / USA-прокси / напрямую                                      |
| Сертификаты и продление | acme.sh (cron)                 | выпуск и обновление, smartdns перечитывает раз в час                    |
| Запуск                  | systemd-юнит                   | автостарт, рестарт при падении                                          |

## Почему фолбэк сделан внутри, а не средствами ОС

Стандартный stub-резолвер **не продолжает цепочку на NXDOMAIN** — это  
окончательный ответ. Он переходит к следующему серверу только при таймауте  
или SERVFAIL. Поэтому «вернуть NXDOMAIN, и система сама спросит другой DNS»  
не работает: система никуда не пойдёт. Приходится перебирать цепочку самим,  
внутри сервера. Именно это и делает `chain`.

## Быстрый старт (macOS)

```bash
# 1. Проверить, как конфиг понят (ничего не запускает):
./smartdns-darwin-arm64 -config smartdns.yaml -check

# 2. Погонять руками на безопасном порту, без sudo:
#    в smartdns.yaml: listen: 127.0.0.1:5353
sudo ./smartdns-darwin-arm64 -config smartdns.yaml -v
# в другой консоли:
dig @127.0.0.1 -p 5353 claude.ai A +short
dig @127.0.0.1 -p 5353 www.workbuddy.ai A +short

# 3. Поставить демоном на 53-й порт:
sudo ./install-macos.sh
```

Apple Silicon → `smartdns-darwin-arm64`, Intel → `smartdns-darwin-amd64`.  
Порт 53 требует root, поэтому демон кладётся в `/Library/LaunchDaemons`  
(это root-контекст) — оттуда он поднимается сам при загрузке и переживает  
перелогин.

Чтобы вся система ходила через него:

```bash
sudo networksetup -setdnsservers Wi-Fi 127.0.0.1 1.1.1.1
sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder
```

Вернуть как было: `sudo networksetup -setdnsservers Wi-Fi empty`

Удаление: `sudo ./install-macos.sh --remove`

### Windows

```bat
install-windows.bat          (от администратора)
```

Ставит службу `smartdns` с автозапуском, сам себе подсовывает абсолютный путь  
к конфигу (служба стартует с рабочим каталогом `System32`, относительные пути  
там не работают). `smartdns.exe -service stop|start|remove`.

## Конфиг

```yaml
listen: 127.0.0.1:53    # или список адресов (см. ниже «listen как список»)
ipv6: false          # false — вырезаем IPv6
timeout: 4s          # сколько ждать каждый сервер цепочки
log: ""              # пусто — в консоль
verbose: true        # видно всю цепочку и причину отбраковки

reject:              # что считаем «погадил»
  networks: [0.0.0.0/8, "::/128", 127.0.0.0/8]
  empty_a: true      # NOERROR без единой A-записи
  rcodes: [SERVFAIL, REFUSED, NOTIMP]

cache:
  enabled: true
  max_entries: 10000
  min_ttl: 10
  max_ttl: 86400
  negative_ttl: 60

servers:             # имя -> адрес
  ru: 111.88.96.50
  rudoh: https://xbox-dns.ru/dns-query
  cf: 1.1.1.1
  g: 8.8.8.8

hosts:               # статические ответы, резолвер не спрашиваем вовсе
  "*.doubleclick.net": nxdomain
  "my.local.test": 10.0.0.7

routes:              # первое совпадение выигрывает
  - match: [claude.ai, openai.com, anthropic.com]
    chain: [ru, cf, g]
  - match: ["*"]
    chain: [cf, g]
```

### `servers`

Ключ — любое имя, оно же используется в `chain`. Значение:

| Формат                          | Что это                                                 |
| ------------------------------- | ------------------------------------------------------- |
| `1.1.1.1`                       | обычный DNS, порт 53                                    |
| `1.1.1.1:5353`                  | обычный DNS с портом                                    |
| `tls://164.215.97.95`           | DoT, порт 853 (можно и явно `:853`)                     |
| `tls://[2606:4700:4700::1111]`  | DoT по IPv6. Скобки обязательны, без скобок тоже поймёт |
| `https://xbox-dns.ru/dns-query` | DoH (POST)                                              |

Для DoT адрес задаётся IP или доменом, порт 853 подставляется сам.  
`ServerName` для проверки сертификата берётся из адреса — это важно, когда  
сертификат выпущен на IP (как наш Let's Encrypt shortlived на 164.215.97.95).

DoT-соединение **переиспользуется**: на каждый запрос новое не открывается.  
Это не микрооптимизация, а необходимость — если апстрим сидит за прокси с  
дорогим установлением потока, открытие TCP+TLS на каждый чих уезжает в  
секунду (у нас на USA-прокси: ~600 мс handshake против ~120 мс сам запрос).  
Умершее соединение переоткрывается прозрачно, поэтому простоев не видно.

Если адрес DoH — домен, его резолвит системный резолвер машины  
(это нормальный bootstrap; цепочка обязана где-то обрываться на IP).

### `warm` — держать каналы тёплыми

```yaml
warm: 4s                          # как часто слать запрос, чтобы поток не умер
warm_name: example.com            # чем именно, если актуализировать нечего
warm_servers: [cf6a, cf6b]        # необязательно: греть только эти апстримы
prefetch: true                    # тратить эти запросы на актуализацию кэша
```

Зачем: установление потока через прокси может стоить в пять раз дороже  
самого запроса. На USA-прокси это 600 мс против 120 мс, и без прогрева их  
платит первый же запрос после старта или после паузы. С прогревом —  
промах всегда ~120 мс, разницы с «быстрым» путём нет.

Интервал выбирается по таймауту простоя на пути, а не по вкусу: USA-прокси  
убивает **любой** простаивающий поток меньше чем через 10 секунд, и UDP, и  
TCP. Замерено:

```
UDP-сокет через USA-прокси:  5 с простоя -> 124 мс   10 с -> 601 мс
DoT-соединение:              сразу 122 мс            10 с -> соединение мертво
```

Поэтому 5 с — не «на всякий случай почаще», а потолок. 30 с уже не работает.

Для UDP держится пул из четырёх **присоединённых** сокетов: штраф платится  
за новый 5-tuple, а не за направление, так что переиспользовать надо именно  
сокет. Тонкость: присоединённый сокет, с которого ещё не ушло ни одного  
пакета, потока не создаёт, — поэтому греется каждый слот пула, а не один.

### `prefetch` — те же запросы актуализируют кэш

Раз трафик всё равно обязан идти каждые несколько секунд, бессмысленно  
тратить его на фиктивное имя. С `prefetch: true` прогрев переспрашивает те  
записи кэша, которым осталось жить меньше двух интервалов, и кладёт свежий  
ответ обратно. Клиент в итоге не видит промахов вообще: запись обновляется  
до того, как истечёт.

```yaml
prefetch: true
```

Как выбирается, что спросить:

1. Из кэша берутся записи, которые истекут в ближайшие `2 × warm` (но не  
   меньше 10 с) **и** которыми пользовались в последний час. Сортировка —  
   по скорейшему истечению.
2. Очередь расходится по тикам и по греемым апстримам: два апстрима с  
   `warm: 4s` дают тик каждые 2 с, а не 4.
3. Если обновлять нечего — холостое имя `warm_name`, чтобы канал не остыл.

Замер на vdska (один греемый апстрим, `max_ttl: 20 s`, опрос каждые 2 с):

|                   | промахи за 70 с                     |
| ----------------- | ----------------------------------- |
| `prefetch: false` | каждые 13–22 с, ровно по TTL записи |
| `prefetch: true`  | один, на старте; дальше всё из кэша |

В бою, на настоящих TTL (80 с наблюдения, четыре домена): ответ 0–1 мс всё  
время, TTL у короткоживущих записей скачет обратно вверх —  
`14 → 10 → 8 → 15`, `6 → 48`, `9 → 23 → 18 → 14 → 9 → 60`. Ни одного промаха.

Две тонкости, из-за которых иначе получается ерунда:

- Актуализация **не** обновляет «давность обращения» записи. Обнови она —  
  запись, которой перестали пользоваться, считалась бы живой вечно и вечно  
  тянула бы трафик. Так она отпускается через час после последнего  
  настоящего запроса клиента.
- TTL в ответе зажимается в `[min_ttl, max_ttl]`, и хранится зажатым. Без  
  этого ответ обещал бы больше, чем запись живёт: при `max_ttl: 20` клиент  
  видел `41` и считал ответ валидным ещё 41 с, хотя мы его выбросили через 20.

### `routes`

`match` — имя или суффикс: `claude.ai` покроет и `claude.ai`, и  
`www.claude.ai`. `*.claude.ai` — то же самое, просто явнее.  
`match: ["*"]` — всё остальное, пишется последним.

`chain` перебирается по порядку: **первый сервер, чей ответ не отбракован, и  
есть ответ**. Поэтому «умный» ставится первым, чистый — вторым.

### `hosts`

Значение: IP, домен (получится CNAME), `nxdomain` или `refused`.  
Можно несколько через запятую. Ключ вида `"*.domain"` работает как суффикс —  
обычный `/etc/hosts` так не умеет (там только точные имена).

### `reject`

| Правило    | Суть                                           |
| ---------- | ---------------------------------------------- |
| `networks` | если в ответе есть адрес из этих сетей — мусор |
| `empty_a`  | NOERROR без единой A-записи — мусор            |
| `rcodes`   | эти коды — идём дальше по цепочке              |

Добавьте `NXDOMAIN` в `rcodes`, если ваш резолвер врёт «имени нет» вместо  
подмены. Ничего страшного: реально несуществующее имя просто пройдёт всю  
цепочку и всё равно вернёт NXDOMAIN.

## Кэш: когда он сбрасывается

Кэш живёт **в памяти**, на диск не пишется.

| Событие                      | Что происходит                                                       |
| ---------------------------- | -------------------------------------------------------------------- |
| Истёк TTL записи             | запись сама вылетает (плюс раз в минуту проходит чистка)             |
| Ответ пришёл с TTL=0         | не кэшируется вообще                                                 |
| Переполнение (`max_entries`) | вытесняются сначала просроченные, потом самые давние                 |
| `kill -HUP <pid>`            | конфиг перечитан, **кэш сброшен целиком**                            |
| `kill -USR1 <pid>`           | кэш сброшен целиком, вручную                                         |
| Рестарт процесса             | кэш пуст — он никуда не сохранялся                                   |
| Мусорный ответ               | **никогда не попадает в кэш**                                        |
| Актуализация (`prefetch`)    | запись **перезаписывается**, а не вылетает; кэш целиком не трогается |

TTL берётся минимальный среди всех записей ответа и зажимается в  
`[min_ttl, max_ttl]`. Пустые ответы и NXDOMAIN помнятся `negative_ttl`  
секунд (по умолчанию 60).

При отдаче из кэша TTL уменьшается на время хранения: закешировали с TTL 300,  
через 4 секунды отдали 296. Иначе клиент получил бы «свежий» TTL от записи,  
которой осталось жить несколько секунд.

`kill -USR2 <pid>` — показать в логе: сколько записей, попаданий, промахов.

> **Грабли, на которых кэш молча умирал.** OPT (EDNS0) — псевдо-запись: её  
> поле TTL на самом деле содержит расширенный RCODE, версию и флаги, и почти  
> всегда равно `0`. Если считать его обычной записью, минимальный TTL любого  
> ответа станет нулевым, и «TTL=0 — не кэшировать» отключит кэш целиком.  
> А OPT присылают все современные резолверы, потому что `dig`, браузеры  
> и sing-box сами шлют EDNS0. Симптом: в логе `попаданий 0` при растущем  
> числе записей. Лечится тем, что OPT при подсчёте TTL пропускается.

### Когда кэш имеет смысл сбрасывать руками

Практика обычная: **после любой смены маршрута, сети или DNS-сервера** —  
потому что закэшированный адрес может указывать туда, куда вы уже не ходите.  
Типичные случаи:

- переключились на другой VPN/туннель или выключили его;
- поменяли `routes` в конфиге (впрочем, `kill -HUP` сбрасывает сам);
- резолвер придумал новый адрес-реле, а вы всё ещё ходите на старый;
- отлаживаете и хотите видеть настоящий ответ, а не сохранённый.

Системный кэш чистится отдельно — он поверх нашего:

```bash
# macOS
sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder

# Windows
ipconfig /flushdns

# Linux (systemd-resolved)
sudo resolvectl flush-caches

# Chrome держит свой кэш: chrome://net-internals/#dns
```

Ориентир по TTL в природе: у CDN 60–300 с, у обычных доменов 300–3600 с,  
NS/SOA до суток. Подмены от «умного» резолвера обычно приходят с TTL 60 —  
то есть свежий адрес подхватывается не позднее чем через минуту.

## IPv6

`ipv6: false` (по умолчанию):

- на запрос `AAAA` отвечаем **пустым NOERROR** (не NXDOMAIN — чтобы клиент не  
  решил, что имени нет);
- из чужих ответов выкидываем все `AAAA`;
- из `HTTPS`/`SVCB` вырезаем параметр `ipv6hint` (RFC 9460, ключ 6) — иначе  
  браузер узнает IPv6-адрес, даже не спрашивая AAAA.

`ipv4hint` при этом сохраняется — он полезен.

## Важно: DNS и трафик должны идти в одну сторону

Подменённые адреса (`87.228.47.x`, `8.47.69.x`, пул Selectel в Питере)  
**не отвечают не-российским IP** — проверено: из Финляндии они молчат.  
Поэтому мало направить DNS на `ru`: сам трафик к этим адресам тоже должен  
идти через Россию. Иначе цепочка отработает, но соединения не будет.

Отсюда правило: в клиенте (sing-box/Throne) маршрут для этих доменов и  
`chain` в конфиге должны совпадать. Автоматически из маршрутов это не  
выводится — настраивается в двух местах.

```
ОК       A     claude.ai            87.228.47.204     ru OK
ФОЛБЭК   A     www.workbuddy.ai     CNAME dad483...   ru[A 0.0.0.1 из 0.0.0.0/8] -> cf OK
БЛОК     AAAA  google.com           -> пустой NOERROR (IPv6 вырезан)
ХОСТ     A     ads.doubleclick.net  -> nxdomain
КЭШ      A     claude.ai
СБОЙ     A     example.com          никто из цепочки не ответил: ru(ошибка) -> cf(ошибка)
```

`ПОГАНЫЙ` означает: вся цепочка погадила, а мы всё равно отдали последний  
ответ — SERVFAIL был бы хуже, потому что система всё равно никуда не пойдёт.

## DoT: свой `tls://` вместо чужого

smartdns умеет не только слушать UDP, но и отдавать **DNS-over-TLS** — тогда  
клиент (Throne/sing-box) стучится к вам, а не к 9.9.9.9. Плюс: ответы  
кэшируются на вашем сервере, и цепочка туннелей не загружается DNS-ерундой.

```yaml
listen: 127.0.0.1:5354     # обычный UDP/TCP — сюда может стучаться свой же sing-box

dot:
  listen: 0.0.0.0:853      # сюда стучится клиент: tls://<ваш IP>
  cert: /root/.acme.sh/164.215.97.95_ecc/fullchain.cer
  key:  /root/.acme.sh/164.215.97.95_ecc/164.215.97.95.key
```

Что важно:

- **Нужен сертификат с IP в SAN** (или с hostname, куда вы резолвитесь).  
  Let's Encrypt такие выдаёт, но только с профилем `shortlived` — живут  
  ~7 дней:
  ```bash
  acme.sh --issue -d <ВАШ_IP> --standalone --ecc \
          --server letsencrypt --certificate-profile shortlived
  acme.sh --install-cronjob     # продление раз в сутки
  ```
  smartdns перечитывает файл сертификата раз в час и по `kill -HUP`, так что  
  продление подхватывается без перезапуска.
- DoT слушает на `tcp-tls`; обычный `listen` поднимает и UDP, и TCP.
- Слушатель на `0.0.0.0` — это открытый резолвер. Для DoT это терпимо  
  (усилить атаку нечем: клиент обязан пройти TLS). **А вот публичный UDP 53 —  
  готовый усилитель для DDoS-амплитфикации** (25×–70× на DNS-ответах), так что  
  его открываем только если понимаем, что делаем, и держим наготове ufw.
- Биндиться на публичный 53 в Ubuntu надо **на конкретный IP** (`164.215.97.95:53`),  
  не на `0.0.0.0` — wildcard конфликтует с `systemd-resolved`, который сидит  
  на `127.0.0.53:53` и `127.0.0.54:53`.

### `listen` может быть списком

```yaml
listen:
  - 127.0.0.1:5354     # для своего же sing-box
  - 164.215.97.95:53   # публичный классический UDP+TCP DNS
```

Старый вид (`listen: 127.0.0.1:53` — одна строка) тоже понимается. Каждый  
адрес поднимается и на UDP, и на TCP; дубликаты адресов (в `listen` или  
между `listen` и `dot`) отвергаются при старте.

### `dot` с несколькими сертификатами: маршрутизация по SNI

`dot` может быть списком (несколько портов), но когда порт один, а сертификата  
нужно два — по имени и по IP — используется `named`:

```yaml
dot:
  - listen: 0.0.0.0:853
    # дефолт: отдаётся тем, кто не прислал узнаваемого имени в SNI
    cert: /root/.acme.sh/164.215.97.95_ecc/fullchain.cer     # shortlived IP-серт
    key:  /root/.acme.sh/164.215.97.95_ecc/164.215.97.95.key
    named:
      - server_name: 164.215.97.95.sslip.io
        cert: /root/.acme.sh/164.215.97.95.sslip.io_ecc/fullchain.cer
        key:  /root/.acme.sh/164.215.97.95.sslip.io_ecc/164.215.97.95.sslip.io.key
```

Правила выбора сертификата на рукопожатии:

| Клиент прислал в SNI                      | Какой сертификат    |
| ----------------------------------------- | ------------------- |
| имя из `named` (`164.215.97.95.sslip.io`) | именной, `CN = имя` |
| IP-литерал или мусор                      | дефолт              |
| ничего (нет SNI)                          | дефолт              |

Имя сравнивается **без учёта регистра** (RFC 6066) — `164.215.97.95.SSLIP.IO`  
в SNI тоже получит именной сертификат.

Go-клиенты (Throne/sing-box, doggo) при подключении **по IP не шлют SNI  
вовсе** — поэтому им достаётся дефолт. Тот же Go-клиент по имени шлёт  
`ServerName = 164.215.97.95.sslip.io` — и получает именной. Один порт, оба  
мира. Проверка: `openssl s_client -connect IP:853 -servername имя` против  
`openssl s_client -connect IP:853`.

Старые виды — `dot:` один объект или список без `named` — тоже понимаются,  
ничего ломать не надо.

### Грабли: один сертификат не может иметь одновременно CN и IP

Проверено на тестовом контуре Let's Encrypt, и это не лечится:

| Профиль                | Subject (CN) | IP в SAN     | Срок    |
| ---------------------- | ------------ | ------------ | ------- |
| `shortlived`           | **пустой**   | разрешён     | ~7 дней |
| классический (default) | `CN = имя`   | **запрещён** | 90 дней |

На попытку запихнуть IP в классический профиль LE отвечает:

```
"detail": "Error creating new order :: Default profile does not permit IP address identifiers."
```

А `shortlived`-сертификат приходит с **пустым subject**. Это не косметика:  
**любой клиент на GnuTLS роняет на нём рукопожатие** — разбор DN нулевой  
длины валится ещё до проверки цепочки:

```
gnutls[3]: ASSERT: lib/x509/dn.c[_gnutls_x509_get_dn]:221
;; WARNING: TLS, handshake failed (The requested data were not available.)
```

Проверено к controlled-экспериментом: тот же ключ, серт с пустым subject →  
ровно эта ошибка; серт с `CN` → рукопожатие проходит. `openssl s_client` и  
`gnutls-cli` при этом говорят «доверяю» — оба врут, потому что не вызывают  
тот же код проверки.

Поэтому серт на имя нужен обязательно, а IP-серт хочется оставить. Раньше  
это решалось **двумя портами** (853 — имя, 8853 — IP), но клиент вроде Throne  
порт DoT менять не может. Поэтому теперь один порт 853 и **выбор сертификата  
по SNI** (см. `named` выше):

- клиент стучится `tls://164.215.97.95.sslip.io` → SNI с именем → серт с CN,  
  который принимает **каждый** (Go, OpenSSL, GnuTLS, kdig с `+tls-sni`);
- клиент стучится по IP (`tls://164.215.97.95`) → Go не шлёт SNI → дефолтный  
  IP-серт, пустой subject ему безразличен.

Оговорка про kdig: наш билд почему-то не выставляет SNI по умолчанию, поэтому  
по имени он получает дефолтный IP-серт и падает на пустом subject. Лечится  
явно: `kdig @164.215.97.95.sslip.io +tls +tls-sni=164.215.97.95.sslip.io ...`.

Бесплатное имя под 853 даёт `sslip.io`: `<ваш-IP>.sslip.io` резолвится в  
ваш IP, CAA на зоне нет, так что выпустить можно. Проверено:

```bash
acme.sh --issue -d 164.215.97.95.sslip.io --standalone --keylength ec-256
# -> subject=CN = 164.215.97.95.sslip.io, 90 дней
```

Два «но»: у LE лимит 50 сертов в неделю на зарегистрированный домен делится  
на всех пользователей `sslip.io`, и продление завязано на то, что сервис  
жив. Свой домен (`.top` — $4.63 за продление) снимает обе зависимости.

### Пример: vdska

Смысл — вынести DNS из WARP-цепочки. Раньше sing-box слал каждый запрос в  
`1.1.1.1` через WARP (124 мс и лишний трафик через IPv6-прокси). Теперь он  
спрашивает `127.0.0.1:5354`, а smartdns на промахе идёт к апстриму.

Апстримов два, и оба американские — но разными путями:

```yaml
servers:
  cfw: 1.1.1.1                        # через WARP: ip rule add to 1.1.1.1/32 table 100 pref 99
  cf6a: tls://[2606:4700:4700::1111]  # напрямую в USA-прокси по IPv6, БЕЗ WARP
  cf6b: tls://[2606:4700:4700::1001]
  l3a: 4.2.2.1                        # последний рубеж, напрямую (Европа, но живой)
  l3b: 4.2.2.2
routes:
  - match: ["*"]
    chain: [cfw, cf6a, cf6b, l3a, l3b]
```

Зачем второй, если первый работает: `4.2.2.x` резолвит из Дублина, то есть  
раньше падение WARP означало не просто «DNS медленнее», а **смену гео** —  
трафик идёт из США, а CDN даёт европейские адреса. DoT по IPv6 эту дыру  
закрывает: он идёт через тот же USA-прокси, но минуя WARP.

Почему именно IPv6: USA-прокси наружу смотрит **только в IPv6**. UDP на  
`8.8.8.8` через него просто не отвечает, а `[2606:4700:4700::1111]:853` —  
работает. То есть IPv6-адрес апстрима тут не прихоть, а единственный вариант.

Доезжает он policy-routing'ом — нужны маршруты до адресов апстрима в TUN  
sing-box (прописаны в `/usr/local/bin/warp-usa-up.sh`, переживают ребут):

```bash
ip -6 route replace 2606:4700:4700::1111/128 dev tun-usa src fd00:1::1
```

Проверялось так: `ip route add unreachable 1.1.1.1/32 table 100` (WARP для  
DNS умирает), рестарт, запрос. В логе:

```
ФОЛБЭК  A  netflix.com  52.3.144.142  cfw(ошибка) -> cf6a OK
```

То есть гео осталась американской при мёртвом WARP.

В sing-box:

```json
"dns": {
  "servers": [
    {"type": "udp", "tag": "dns-local", "server": "127.0.0.1", "server_port": 5354},
    {"type": "udp", "tag": "dns-us", "server": "1.1.1.1", "detour": "warp-usa-out"}
  ],
  "final": "dns-local"
}
```

Второй сервер оставлен для отката: вернуть как было — поменять `final`  
обратно на `dns-us`. Клиенту в Throne: `tls://164.215.97.95.sslip.io`  
(по имени — серт с CN; `tls://164.215.97.95` тоже работает — по IP достанется  
IP-серт, Go-клиенту всё равно). Публичный классический DNS на  
`164.215.97.95:53` — для тех, кому DoT недоступен.

systemd-юнит и сам конфиг — в пакете развёртывания `vdska-deploy.zip`
(вместе с маршрутами WARP, юнитами и инструкцией по сертификатам).

### Про гео ответов — честно

Утверждение «4.2.2.1 — резолвер в Ричмонде, гео американская» **опровергнуто**.  
Решающий тест — `netflix.com`, он живёт на AWS и отвечает разными адресами  
для разных регионов:

| апстрим                                         | `netflix.com`                                | что это                      |
| ----------------------------------------------- | -------------------------------------------- | ---------------------------- |
| `4.2.2.1` напрямую                              | `3.251.50.149, 54.155.178.5, 54.74.73.31`    | AWS **eu-west-1, Дублин**    |
| `1.1.1.1` через WARP                            | `3.230.129.93, 52.3.144.142, 54.237.226.164` | AWS **us-east-1, Вирджиния** |
| `tls://[2606:4700:4700::1111]` через USA-прокси | те же `3.230.x / 52.3.x / 54.237.x`          | AWS **us-east-1, Вирджиния** |
| `8.8.8.8` через USA-прокси                      | не отвечает вовсе                            | прокси не умеет в IPv4       |

Дополнительно: `dig TXT o-o.myaddr.l.google.com` показывает, какой IP видит  
Гугл у резолвера. Для `4.2.2.1` это `8.0.18.x` (Level3, US) — но это адрес  
*эгресса Level3*, а не местоположение узла, который вам ответил; до него  
30 мс, то есть отвечает европейская инстанция. Поэтому гео-базы «Канзас»  
и живые ответы «Дублин» не противоречат друг другу.

Отсюда правило: **гео DNS должна совпадать с гео выхода**, иначе получается  
тот самый разнобой, когда трафик выходит из США, а CDN подсовывает  
европейские адреса. Быстроту даёт кэш (промах ~124 мс, попадание 0 мс).

Задержки замерялись с самой vdska:

| путь                                          | первый запрос     | последующие |
| --------------------------------------------- | ----------------- | ----------- |
| UDP `1.1.1.1` через WARP                      | ~124 мс           | ~124 мс     |
| DoT `[2606:4700:4700::1111]` через USA-прокси | ~620 мс (TCP+TLS) | ~120–160 мс |
| то же, с прогревом `warm: 5s`                 | **~120 мс**       | ~120 мс     |

Разница только на установлении потока. WARP её не платит, потому что  
WireGuard-туннель уже поднят и поток через прокси жив; DoT платил один раз —  
пока мы не научили его держать соединение и прогревать.

### Выбор резолвера: «самый быстрый на Восточном побережье» не существует

Замеряли 18 публичных резолверов по IPv6 через USA-прокси, тёплым каналом:

| резолвер                            | UDP тёплый | DoT тёплый |
| ----------------------------------- | ---------- | ---------- |
| Hurricane Electric `2001:470:20::2` | 113 мс     | 114 мс     |
| Cloudflare `2606:4700:4700::1001`   | 117 мс     | 123 мс     |
| Google `2001:4860:4860::8888`       | 119 мс     | 122 мс     |
| Cloudflare `2606:4700:4700::1111`   | 121 мс     | 119 мс     |
| Quad9 `2620:fe::fe`                 | 125 мс     | 125 мс     |
| Verisign `2620:74:1b::1:1`          | 123 мс     | —          |
| AdGuard `2a10:50c0::ad1:ff`         | 142 мс     | 145 мс     |
| CleanBrowsing `2a0d:2a00:1::`       | 357 мс     | 360 мс     |

Разброс у лидеров 113–125 мс — это шум: все они anycast и все отвечают из  
одного и того же американского PoP. 120 мс — задержка самого USA-прокси, а не  
резолвера, поэтому «найти самый быстрый DNS» тут нельзя по определению.  
Выбор пал на Cloudflare: он в лидерах, оба адреса работают, сертификат  
проверяется, гео американская.
